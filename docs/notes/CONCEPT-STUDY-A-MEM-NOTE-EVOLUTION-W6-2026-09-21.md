# A-MEM note-evolution / neighbor-merge: adopt the disposition seam, SKIP the unattended rewrite

> Studied 2026-09-21. Sources: [A-MEM, arXiv:2502.12110](https://arxiv.org/abs/2502.12110) (NeurIPS 2025); [Mem0, arXiv:2504.19413](https://arxiv.org/abs/2504.19413); [agent-memory survey, arXiv:2602.06052](https://arxiv.org/abs/2602.06052); counter-evidence: [Letta benchmarking post](https://www.letta.com/blog/benchmarking-ai-agent-memory/), [Memanto, arXiv:2604.22085](https://arxiv.org/abs/2604.22085), [arXiv:2606.24775](https://arxiv.org/abs/2606.24775), [StructMemEval, arXiv:2602.11243](https://arxiv.org/abs/2602.11243). Tracker: [#2625](https://github.com/anthony-chaudhary/fak/issues/2625). Parent epic: [#2618](https://github.com/anthony-chaudhary/fak/issues/2618). Feeds: [memory-concept rankings #2237](../superset/MEMORY-CONCEPT-RANKINGS.md).

## Verdict

**SKIP the unattended neighbor rewrite; ADOPT nothing new as a build.** FAK already holds the load-bearing half of A-MEM's "memory evolution" — consolidation, structural retirement, and verified recall — at a lower risk than an LLM rewriting a peer note on every insert. The value A-MEM buys with neighbor-rewrite is real but narrow (multi-hop association), while its costs (multiple LLM calls per insert, non-idempotent body replacement, nondeterminism) land directly on three FAK invariants: [expire-by-default / no-hard-delete](../CONTEXT-IS-NOT-MEMORY.md), the [shared multi-session tree](../../AGENTS.md) (a background merge racing a live edit), and deterministic replay.

Per-mechanism verdicts:

1. **A-MEM neighbor-rewrite on insert — SKIP.** It replaces `m_j` with `m_j*` (`m_j* ← LLM(...)`; "the evolved memory m_j* then replaces the original memory m_j"), i.e. a non-idempotent, nondeterministic mutation of a note FAK does not own. The rewrite is not *only* destructive: it also *enriches* neighbors with added context/keywords/tags (bidirectional). But the SKIP reasoning governs both halves — an additive LLM write to a peer note is still non-idempotent (a replay does not reproduce the store), still nondeterministic ("different LLMs generate slightly different contextual descriptions"), and still races a live edit on the shared multi-session tree. The destructive half additionally lands against `internal/memq/doc.go:31-34` ("There is NO hard-delete operator"). The 2026 study arXiv:2606.24775 independently recommends "conservative memory consolidation … localized maintenance is more cost-efficient than global reorganization" and warns semantic consolidation "destroys crucial chronological cues."
2. **A-MEM link generation (decide whether to link) — SKIP as an LLM rung; already covered structurally.** Deterministic `[[wikilink]]` extraction + backlink/index resolution already exists (`internal/memq/notesbackend.go:199-204`, `resolveWikiLinks` at `:255-280`); author-declared supersession edges cover correction (W5, `internal/recall/supersede.go:32`). An LLM link proposer adds a nondeterminism seam without a witness that it beats the declared edge.
3. **Mem0 UPDATE-style conflict resolution on write — PARTIAL / SKIP as-is.** FAK has the *negative-only* half: `supersedes:` retires the stale note while bytes and row survive (`notesbackend.go:103-115`; `supersede.go:5-10`). Mem0's ADD/UPDATE/**DELETE** engine physically mutates; the graph variant already reports that marking invalid beats removing. Adopt the mechanism only if a later dogfood shows the declared edge is too much authoring burden — then it must be proposal-only.
4. **Consolidation / dedup / forgetting lifecycle layer — ADOPT (already shipped, in different leaves).** `memq consolidate` produces a real derived disposition but never writes it back durably (`internal/memq/exec.go:744-783`, `Applied:false`; write-back is the named rung-2 follow-on [#3906](https://github.com/anthony-chaudhary/fak/issues/3906)); `recall.Dream` is the deterministic offline reseal pass that **never** summarizes with a model (`internal/recall/dream.go:64-68`); the fleet lessons write-time dedup guard is [#2142](https://github.com/anthony-chaudhary/fak/issues/2142) (`internal/fleetmemory/dedup.go:34`); the read-time verifier withholds a note whose named SHA/path/flag no longer resolves (`internal/recall/reverify.go:105,251`; applied at `notesbackend.go:310-328`). Do not add a second consolidation layer.
5. **Proposal-only disposition surface (the one genuinely absent seam) — SKIP for now, WATCH.** If W6 ever ships, it must be an *op* alongside `consolidate` (`internal/memq/memq.go:73`), emitting a proposal through the existing promotion/disposition gate and never an unattended write to a peer's note — the same posture `memq` already enforces (effects default to PROPOSED; `doc.go:35-38`). Because `consolidate`'s durable write-back is still rung-2 and unshipped, a neighbor-merge proposal has no durable target to land in yet. Building it now would be a speculative layer ahead of its substrate, which the [spine-first default](CONCEPT-MEMORY-VALUE-UNBOUNDED-SCORE-2026-07-03.md) forbids.

**Counter-evidence weighed, not ignored.** Letta reports a bare filesystem agent at **74.0% on LoCoMo** vs "Mem0's reported 68.5% score for their top-performing graph variant," arguing "even simple filesystem tools are sufficient to perform well on retrieval benchmarks." Memanto (single typed query) reports LongMemEval 89.8% / LoCoMo 87.1% "incurring no ingestion cost," framing graph complexity as a "Memory Tax." StructMemEval reports many memory capabilities "can often be achieved with simple retrieval-augmented LLMs." Three independent sources, all non-peer-reviewed (blog / single-version preprints, some company-authored), but they point the same way: a rewrite pipeline is not what moves the number. This is the falsifier for the A-MEM side: its own reported gains are vs older baselines (MemGPT/LoCoMo), and Mem0's re-run places A-MEM well below Mem0.

**Already in our own doctrine.** FAK did not arrive at this SKIP blind: [`CONTEXT-IS-NOT-MEMORY.md:421`](../CONTEXT-IS-NOT-MEMORY.md) already tabulates A-MEM's "memory evolution" as "Dynamic organization, not a promotion gate; no transient filter", and [`CONCEPT-MEMORY-IN-THE-LOOP-2026-07-02.md:46-51`](CONCEPT-MEMORY-IN-THE-LOOP-2026-07-02.md) already records that "what nobody does: re-verify recalled memory against ground truth at injection" is FAK's differentiating read-time verifier. W6 therefore adds no new mechanism; it closes the loop on a decision the doctrine had already gestured at. (`fak flow prior-art` returned `NO EVIDENCE — novel or unmined` (code=0 notes=0 registry=0) for the *neighbor-merge* mechanism itself — honest, and consistent with this being a research decision rather than an unmined implementation.)

## Value frame

- **For:** FAK-owned long-running agent loops whose `[[wikilink]]` store grows monotonically and accumulates semantically-equivalent or alias notes that never merge.
- **Problem:** the store has no note-body merge/alias mechanism at all — `NotesBackend` explicitly "opens no file for write and implements neither Tombstoner nor Pruner" (`internal/memq/notesbackend.go:35-36`), and the only "alias" is content-addressed same-digest detection in `recall.Dream` (`DreamActionDuplicateAlias`, defined `dream.go:16-23`; used `dream.go:99-104`) that keeps one CAS copy without re-pointing links.
- **Today:** append + author-declared supersession ([#2624](https://github.com/anthony-chaudhary/fak/issues/2624)) + verified recall ([#2395](https://github.com/anthony-chaudhary/fak/issues/2395)) + human/skill-driven [`memory-compact`](../../.claude/skills/memory-compact/SKILL.md) cover correction, staleness, and hot/cold tiering; only true *body merge* is absent.
- **Better because:** SKIP keeps the store deterministic and peer-safe; the absent merge value is recovered instead by the already-shipped proposal-only `consolidate` artifact plus the skill-driven `memory-compact` pass (MERGE ≠ DELETE), both of which route through a human/disposition gate rather than rewriting a neighbor unattended.
- **Witness:** this dossier is the deliverable — a sourced decision with per-mechanism verdicts. No production code is required; the acceptance for #2625 is "a decision, and SKIP is a valid, witnessed outcome." Re-litigation is prevented by the Excluded list below.

## Negative knowledge

- A-MEM's evolution step is the *most contested* part of its design, not its strongest. Its reported gains are against older baselines (MemGPT / LoCoMo); Mem0's re-run places A-MEM below Mem0. Treat "A-MEM does X" as prior art to weigh, not a result to adopt.
- "Memory evolution" is non-idempotent by construction: `m_j* replaces m_j`. Re-running the pass on the same insert does not reproduce the same store, so it cannot be replayed or verified deterministically — the opposite of FAK's `memq` determinism witness (`memq/doc.go:45-47`).
- The 2026 consolidation consensus is **weaker on "rewrite neighbors"** and stronger on dedup + conflict-flag + forgetting as *lifecycle operations*. Those three already exist in FAK leaves; the rewrite is the part with no independent support.
- The three strongest "simple beats complex" counter-results (Letta filesystem, Memanto single-query, StructMemEval) are all non-peer-reviewed — blog / single-version preprints, some company-authored with a product interest. Weight them as directional, but note the pattern repeats independently across three sources.
- A background neighbor-merge races a live edit on the shared multi-session tree. FAK has no note-body write path in the backend precisely so a scan can never mutate a peer's file mid-session; adding one re-introduces the collision the read-only backend was designed to avoid.
- "no-churn" is **not** a literal policy token anywhere in the tree; it is the informal name for the negative-only / expire-by-default posture declared at `internal/memq/doc.go:29-44`. Cite the posture, not an absent literal.
- Do not confuse the **wikimem** W-series ([#2618](https://github.com/anthony-chaudhary/fak/issues/2618) W1–W6; children #2619/#2620/#2621/#2622/#2624/#2625) with the unrelated **blast-radius containment** W1–W8 series ([#2712](https://github.com/anthony-chaudhary/fak/issues/2712), `docs/notes/w1-spine-2713.md` … `w8-bound-2720.md`). Same letter, different program.
- W6 was deliberately gated behind W1–W5. Checked at `2026-09-21`: **W2 (#2620) and W5 (#2624) are CLOSED/shipped** (W2 = the local extractor populating `Cell.Refs`, `notesbackend.go:155,192`; W5 = `resolveSupersession` applied in `notesbackend.go:103-115`); **W1 (#2619, shared `memgraph` extractor), W3 (#2621, graph-neighbor recall), and W4 (#2622, `fak memory graph`) remain OPEN**. There is no `docs/notes/` or `docs/plans/` file *describing* the wikimem W-series — #2618 appears only as a related-epic mention (`docs/notes/2026-07-10-kernelwiki-study.md:169`), and the structural description lives in the backlog census `docs/project-work-backlog-census-2026-07-15.json:8013-8124` and code comments.
