# Harness child tasks: spawn, input queues, and pending execution

Observed: 2026-09-05 (Pacific time). Status: bounded source study; implementation remains tracked below. Source inspection is not execution proof.

For native harness maintainers, the missing integration is parent-scoped prompt-task admission through the existing guarded queue. The current alternative is coordinator retries or synthetic issue tickets for ephemeral child work. Separating durable task intent from an execution handle would make accepted work inspectable before capacity becomes available. This is an Enabling, tier-1 all-in-one capability, also useful to the standalone harness; no runtime or performance gain is claimed here.

Study receipt: `study_9f5ae46d3d43b36bcad5dae422be9500b0aca65cd75274ca3b772c8f69ec9141` (`fak-study/1`). Documentation delivery: [#11842](https://github.com/anthony-chaudhary/fak/issues/11842), under [#3266](https://github.com/anthony-chaudhary/fak/issues/3266).

## Three transferable behaviors

1. **Keep child creation separate from input to a child.** Codex [spawn admission](https://github.com/openai/codex/blob/6af345407d9c2a568da9d01b6c4b81a9e61495c0/codex-rs/core/src/agent/control/spawn.rs#L620-L641) checks capacity and reserves a slot. It then [submits initial input and returns child identity/status](https://github.com/openai/codex/blob/6af345407d9c2a568da9d01b6c4b81a9e61495c0/codex-rs/core/src/agent/control/spawn.rs#L772-L806), without waiting for task completion. Legacy [send_input](https://github.com/openai/codex/blob/6af345407d9c2a568da9d01b6c4b81a9e61495c0/codex-rs/core/src/tools/handlers/multi_agents_spec.rs#L143-L162) targets an existing agent ID: false/omitted interrupt queues input, while true interrupts before delivery. This queue is not evidence of pending child creation; the [execution-capacity check](https://github.com/openai/codex/blob/6af345407d9c2a568da9d01b6c4b81a9e61495c0/codex-rs/core/src/agent/control/execution.rs#L44-L59) can reject admission.
2. **Name what wakes a wait.** Codex legacy [wait_agent](https://github.com/openai/codex/blob/6af345407d9c2a568da9d01b6c4b81a9e61495c0/codex-rs/core/src/tools/handlers/multi_agents/wait.rs#L120-L204) returns already-terminal targets, or waits for the first terminal result and collects other immediately ready results. A coordinator needs an outstanding-target set for wait-all. The newer [wait contract](https://github.com/openai/codex/blob/6af345407d9c2a568da9d01b6c4b81a9e61495c0/codex-rs/core/src/tools/handlers/multi_agents_spec.rs#L280-L288) watches mailbox activity and steered input; waking need not mean completion. Newer [send_message/followup_task](https://github.com/openai/codex/blob/6af345407d9c2a568da9d01b6c4b81a9e61495c0/codex-rs/core/src/tools/handlers/multi_agents_spec.rs#L198-L238) also distinguish a message that does not start a turn from work that can start an idle target. These API generations must not be conflated.
3. **Represent task intent before execution identity and capacity.** LangGraph [Send(node, arg)](https://github.com/langchain-ai/langgraph/blob/81bf17b23123e4ef8b9d5f49fa09a0122fc2edd1/libs/langgraph/langgraph/types.py#L704-L721) describes a node invocation with its own input, including repeated invocations of the same node. The scheduler later [derives a task ID](https://github.com/langchain-ai/langgraph/blob/81bf17b23123e4ef8b9d5f49fa09a0122fc2edd1/libs/langgraph/langgraph/pregel/_algo.py#L970-L997). The async executor [creates submitted futures](https://github.com/langchain-ai/langgraph/blob/81bf17b23123e4ef8b9d5f49fa09a0122fc2edd1/libs/langgraph/langgraph/pregel/_executor.py#L131-L169) while a configured semaphore [delays execution](https://github.com/langchain-ai/langgraph/blob/81bf17b23123e4ef8b9d5f49fa09a0122fc2edd1/libs/langgraph/langgraph/pregel/_executor.py#L214-L217). Transfer the separation between accepted/pending and running work. Graph tasks are not persistent child-agent inboxes; these excerpts alone prove neither bounded backlog admission nor a durable distributed queue.

The adapter witness is the real native tool-to-queue-to-guarded-child path: with active capacity one and backlog capacity two, submit three read-only prompt tasks and observe one running/two queued before collecting independently verified outputs. Replay a submission key without creating another intent, cancel pending work before execution, preserve policy denial, restart the coordinator and recover the same accepted handles, and keep existing issue/lane queue smoke green. A deterministic loopback provider is acceptable only if the actual integration path executes. These are acceptance requirements from #11840, not results of this study.

P1: isolate child context and retain compact verified results. P2: measure admission, execution, and recovery costs against manual bounded delegation before claiming gains. P3: gate the new launch kind and retain issue/lane behavior for rollback. P4: require native harness integration and existing queue witnesses.
