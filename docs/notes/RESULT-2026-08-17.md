# Guarded workflow outcome study — 2026-08-17

## Verdict

The five-pair run supports the **workflow routing default for explicit multi-step, parallel, unattended audit, and mixed-grind work**, but it does **not** support a blanket move from SOL `high` to `xhigh`.

Blind outcome scores were 20/20 correctness and 20/20 usefulness for the default arm versus 10/20 and 10/20 for direct execution. The default arm took 1,786,692 ms versus 1,075,637 ms and produced 46,486 output tokens versus 24,536. Provider-reported input was 10,067,130 versus 7,380,973, but that aggregate hides substantial task-level variance and is not a general token-saving result.

## Frozen envelope

- Five privacy-safe task shapes from the first workflow-default dogfood: trivial, serial multi-step, parallelizable, unattended audit, and mixed grind.
- Both arms used `gpt-5.6-sol`, the same per-task effort, and a declared 12,000-token budget. T1, T3, and T5 used `high`; verification-class T2 and audit-class T4 used `xhigh` in both arms.
- The default arm followed FAK routing: T1 stayed direct; T2–T5 used the guarded workflow path with two declared workers. The direct arm prohibited delegation.
- A separate Claude Opus 5 process received only randomized candidate IDs, frozen prompts/rubrics, and final artifacts. It did not receive arm identity, elapsed time, usage, launch logs, or the private blind map.
- Raw artifacts and the blind map remain in allocated local scratch because model logs can contain repository excerpts. The committed JSON is the privacy-reviewed aggregate emitted by `fak sessions workflow-outcome-study`.

## Routing readout

1. **Keep trivial work direct/high.** T1 was byte-equivalent by design because the default correctly declined orchestration.
2. **Route explicit serial action lists to workflow/high.** T2 improved both quality scores and was faster with less observed input at the route’s actual xhigh effort. The live run exposed and fixed a classifier miss for comma-separated three-action lists.
3. **Keep parallel and mixed-grind workflows at high by default.** T3 and T5 achieved better blind outcomes without xhigh. Their elapsed/token costs show why workflow admission still needs task-shape justification.
4. **Retain xhigh for rigor inside workflows, not for every workflow.** T4's audit route achieved the strongest outcome but cost substantially more elapsed time, input, and output. This supports the existing rigor rule, not expansion of xhigh to grind.
5. **Do not report a universal speed or token gain.** Two workflow tasks were faster or near the direct input cost; two were substantially slower and costlier. The supported claim is outcome quality on this frozen set, with task-dependent cost.

## Operational findings

- Fresh orchestration workers inherited a machine-wide prior-session loop verdict and exited before their first turn. The launcher now disables only that pre-launch historical gate; each child remains guarded and audited during its own execution.
- The launch receipt proves worker start, not completion. The study joined each worker's `turn.completed` usage and extracted final artifact before admitting a completed pair.
- The current workflow implementation delegates one bounded worker and uses its final report as the workflow artifact. Broader lead reconciliation remains a separate productization question; this study does not claim a general N-worker speedup.

## Provenance and uncertainty

- **FAK-authored:** frozen task/rubric contract, routing resolution, launch/audit receipts, artifact digests, evidence-completeness gate, and aggregate join.
- **Provider-observed:** Codex and Claude token counters, model final artifacts, and elapsed process times.
- **Independent judgment:** blinded Claude Opus correctness/usefulness grades.
- **Not established:** statistical generalization beyond five tasks, billed-dollar savings, universal latency improvement, or causal attribution to one internal workflow component.
