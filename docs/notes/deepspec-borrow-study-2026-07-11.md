# DeepSpec borrow study: 0 new issues, the live lead augments #3020 / #3078

*2026-07-11. Study / borrow-scan note (witnessed against the tree, not self-reported).*

## What was studied

[`deepseek-ai/DeepSpec`](https://github.com/deepseek-ai/DeepSpec) @ `005e03b81cec38b7da6399833d609ee89a2587f2` (**MIT**, "The DeepSpec Authors" 2026) — the reference training + evaluation framework for **DSpark** (confidence-scheduled semi-autoregressive speculative decoding), its ablation **DFlash**, and the **Eagle3** baseline. Acquired to a scratch clone; SHA pinned. Method: a four-way fan-out deep-read over the load-bearing subsystems — the DSpark modeling worldview (block drafting + Markov head + confidence head + distribution-matching loss), the eval harness + confidence-scheduling decision rule, the on-disk target-cache/data infra, and the trainer/checkpoint/suspend durability layer — extracting one technique per candidate, license-gating each (default posture: **borrow the technique, reimplement in Go — never vendor**), then **witnessing each candidate against fak's actual tree** and against **prior borrow-scout notes** before filing anything.

The discipline that shaped the outcome (same bar as the [tair-kvcache study](tair-kvcache-borrow-study-2026-07-10.md): *"filing a redundant issue is the failure mode, not the goal"*): a candidate is worth an issue only if it is genuinely absent, high-leverage on fak's axis, **and not already tracked or parked**. That last clause is what set the net result here — fak has already been scouted three times in this exact lane, so the honest move is to augment the existing issues, not open a fourth.

## Net result: 0 new issues; two design reminders recorded on existing issues

The one candidate from DeepSpec that survived the domain filter — **adaptive draft DEPTH driven by a per-token accept signal** — is **not new to fak's backlog**. It has been scouted and deliberately parked twice, and its dispatch-layer analog is already filed:

- **[CONCEPT-STUDY-DSD-DYNAMIC-SPEC-DECODE-2026-07-10.md](CONCEPT-STUDY-DSD-DYNAMIC-SPEC-DECODE-2026-07-10.md)** (Cohere DSD → vLLM) judged the *literal adaptive-K borrow for the pure-kernel spec-decode substrate* **PREMATURE — do not file**: *"A controller that tunes how many draft tokens has nothing to tune until a drafter exists. DSD is strictly downstream of #3197."* Its verdict was to record the idea as a **design reminder on #3078**, not open an issue. It anchors on the same seam this study did (`polymodel.go` `AcceptGreedy`, `verify.go` `VerifyForward`, epic #2236, drafter #3197/#3078).
- **[study-vllm-dynamic-sd-borrow-2026-07-10.md](study-vllm-dynamic-sd-borrow-2026-07-10.md)** (same vLLM PR) reached **0 leaves filed / DIVERGENT** — fak's spec decode isn't a batched serving path, so "K by batch size" is a dormant variable; it notes #3020 already names `accepted_token_ratio` but no by-regime K.
- **[study-mlx-dspark-borrow-scout-2026-07-10.md](study-mlx-dspark-borrow-scout-2026-07-10.md)** (Apple `mlx_dspark`) *did* file **#4199**, but at the **dispatch-governor** level — deriving `loopmgr.Governor.MaxConcurrent` by an argmax over `yield/cost` with a per-run **acceptance EWMA** — and states in its own honest-non-transfer that *"fak's acceptance is per-run not per-position."* That is the loop-concurrency knob, not the token-level draft depth inside the spec kernel.

Filing a fresh "adaptive draft depth" controller issue would therefore dup a twice-parked lead. What DeepSpec adds that those three notes do **not** cover is two narrower, concrete pieces — recorded here as design reminders, not a new issue:

**Reminder A → augments #3020 (and the accounting #3078 will need): a per-POSITION accept-decay profile computed from fak's OWN accept core.**
DeepSpec's harness accumulates `accept_rates_by_position[pos] = accepted_at_pos[pos] / proposals_at_pos[pos]` from exact rejection-sampling accepted-length accounting (`deepspec/eval/base_evaluator.py:496-503, 240-285`). fak today has **only a scalar**: the CPU-synthetic loop that already runs draft→verify→accept→rollback end-to-end accumulates `accepted += res.Accepted` (`cmd/polymodelbench/main.go:285,340`) off `polymodel.AcceptGreedy` (`internal/polymodel/polymodel.go:450`), and #3020 plans a single `accepted_token_ratio` field **read from an external engine's usage block**, not a per-position vector computed from fak's own accept core. Upgrading that scalar to a per-position profile is (i) **not premature** — it instruments the already-green accept path and needs no drafter, (ii) **uncovered** by #4199 (per-run, dispatch-level) and #3020 (scalar, engine-read), and (iii) the empirical substrate any future depth controller (#3078) would consume. This belongs as a **measurement refinement on #3020**, which already owns the spec-decode accounting lane — not a standalone issue that would fragment it.

**Reminder B → augments the #3078 design note: a calibrate-before-exploit reliability gate is the fak-native shape for the eventual depth controller.**
When the depth controller is finally built (downstream of #3197, per the DSD verdict), DeepSpec shows a discipline worth stealing over the DSD lookup-table / mlx-dspark yield-argmax forms: the accept signal is a **learned** per-position head (`AcceptRatePredictor` = `Linear(d,1)`→sigmoid, `deepspec/modeling/dspark/common.py:43-49`, BCE-trained against the measured accept rate, `loss.py:156-163`), and it is **not permitted to schedule depth until it passes a calibration witness** — `--confidence-threshold 0.0` flips the harness into a recording mode that measures the signal's ECE / AUROC / Brier + reliability diagram (`deepspec/eval/dspark/confidence_head.py:30-172`, gated at `evaluator.py:44-48`) before any threshold > 0 truncates a draft (`draft_ops.py:82-93`, `_confident_prefix_length`). That is exactly fak's own `CompareSpeedup` "refuse a speedup unless `QualityParity == verified`" rule (`internal/deepseekbench/deepseekbench.go:263,:68`) and the `calibration_corpus_drift` CI gate — applied to *speculation depth*. Recording this on **#3078** keeps the controller's eventual acceptance rule fak-ethos-shaped (a signal earns the right to shorten drafts only after it is witnessed calibrated) without opening a premature issue.

Net: **0 issues filed.** Two reminders attach to lanes that already exist (#3020, #3078). This is the same choice the DSD note made — record on #3078, do not file — extended with the two DeepSpec-specific details (the per-position profile; the calibration gate) those earlier notes did not carry.

## Dropped as divergent-domain (correct technique, wrong axis for fak)

Load-bearing in DeepSpec because it **trains a draft model offline** and **pre-caches every target hidden state** (~38 TB for Qwen3-4B) on an 8×GPU node. fak neither trains nor caches target hidden states; the Go-native equivalents of the reusable cores are present (above). None filed:

- **mmap-streamed blob-shard + fixed-width packed-binary-index + JSON-manifest cache** with a bounded LRU pool of open shard mmaps (`target_cache_dataset.py:20-22, 77-120, 628-695`).
- **CUDA prefetcher** — side-stream H2D double-buffering with `wait_stream`/`record_stream` ordering (`deepspec/data/cuda_prefetcher.py:14-70`).
- **Two-phase distributed commit** — per-rank private scratch → `dist.barrier` → rank-0 rename+concat finalize, manifest-last commit marker; leader-detect + `broadcast_object_list` consensus (`scripts/data/prepare_target_cache.py:233-394`).
- **Suspend-on-signal at a quiescent boundary** — daemon monitor thread + `threading.Event`, checkpoint-then-exit via the *same* durable save path, rank-0 detect + barrier/broadcast for unanimity (`deepspec/utils/hfai_suspend.py:18-72`, `base_trainer.py:372-405`). Maps onto fak's turn-boundary session-checkpoint + dispatch admission, but the trigger (HPC preemption) and collective mechanics are training-cluster-specific. Present-on-axis / planned; not a borrow.

Not filed.

## Honest fences

- **0 issues filed — and that is the correct outcome, not an under-delivery.** The single domain-relevant lead is a lane fak has already scouted three times (#4199 filed at the dispatch layer; the two DSD notes deliberately parked the kernel-layer controller as premature/downstream of #3197). Opening a fourth issue would dup a parked lead — the exact failure mode this class of note exists to avoid.
- **The two reminders are additive, not a re-file.** Reminder A (per-position accept-decay profile from fak's own accept core) is a measurement refinement on **#3020**; Reminder B (calibrate-before-exploit reliability gate) is a design note on **#3078**. Neither is premature, because A instruments the already-green CPU-synthetic accept loop and B only shapes the eventual controller's acceptance rule.
- **Nothing vendored.** DeepSpec is MIT; the borrowable pieces are idea-level (a per-position accounting shape; a calibration-gate discipline) to be reimplemented in Go against fak's own verify/accept substrate — not a port of `base_evaluator.py` or `draft_ops.py`.
- **Every PRESENT / DROP / DIVERGENT / prior-art verdict is witnessed** against a named `path:line` in this tree or a named sibling note, not against the upstream's plausibility. The scratch clone + fan-out reader outputs are working artifacts, not committed.
