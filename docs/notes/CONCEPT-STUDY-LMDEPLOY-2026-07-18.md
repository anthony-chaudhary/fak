## Worldview (reconstructed from defaults, non-goals, benchmarks)

lmdeploy serves **production Chinese-LLM + InternLM/Qwen deployments** on **NVIDIA GPUs**, optimizing **request throughput** (claims 1.8× vLLM) and **fitting more concurrency into fixed VRAM** via aggressive weight *and* KV quantization. Two engines by design: **TurboMind** (C++, peak throughput) and **PyTorch** (Python, low dev barrier / rapid feature experimentation via a strategy pattern). Defaults betray the priorities: `cache_max_entry_count=0.8` of *free* VRAM to KV; `cache_block_seq_len=64`; `quant_policy=0` (KV quant opt-in, `4`/`8`/`42`); `enable_prefix_caching=False` (correctness-first default); KV quant is **online + data-free** (no calibration corpus blocks deployment). The user is an **ops operator** who wants it to "just work" on any prompt at high RPS, plus a **research user** for whom the PyTorch engine lowers the cost of adding EAGLE/MTP/diffusion decoding as a strategy. This is why their prefix cache keys on **tokens only** (config is process-fixed, so regime-in-the-key is unnecessary *for them*) — a choice fak cannot inherit (see #5273).

## Takeaway

lmdeploy is a **heavily-pre-studied** repo for fak — the #2236 superset epic already ranks against it, and ~11 of the top borrows were already filed (#2240 KV quant, #3175 recurrent-state reuse, #1912 split-fuse, #4202 stochastic spec, #3886 eplb, #4208 draft-vocab, #1266 TurboQuant). The honest residue after on-axis ablation is **3 genuinely-unfiled, ship-alone, CPU-witnessable borrows** (#5271 grammar×spec composition, #5273 regime-fenced cache identity, #5275 expected-drain-time routing), plus a rich reference layer for the already-filed tracks. The single most fak-shaped finding is **#5273**: lmdeploy's token-only cache key is safe *for them* precisely because they lack fak's differentiators (KV quant tiers, hot model-swap, exact eviction, trust plane) — the same features make token-only reuse a correctness hole fak must fence.
