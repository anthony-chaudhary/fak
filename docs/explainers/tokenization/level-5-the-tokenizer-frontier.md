# The tokenizer frontier: how you prove a tokenizer is right

*You are on **Level 5 of 5** of the [tokenization ladder](README.md).*

> **In one breath:** A tokenizer is right when it agrees with the tokenizer the
> model was trained on. This repository checks that against three independent
> references. It also names what it cannot check, and what nobody has solved.

**One line:** Correctness here is not "the code looks right" but "the ids match a
reference implementation the model was actually trained with," witnessed by golden
corpora derived from HuggingFace and llama.cpp, with a separate script that proves
the goldens are genuinely external rather than pasted from this repository's own
encoder; the open edges are greedy BPE's inability to reconsider, a closed
pre-tokenizer dispatch that has already produced one silent-divergence bug, and the
honest scope limit that no tokenizer result certifies model numerics.

> **Audience.** A researcher, a systems lead, or anyone deciding whether to trust
> this component. Prerequisites: Levels [1](level-1-what-is-a-tokenizer.md) through
> [4](level-4-why-the-merge-loop-is-the-hot-path.md). By the end you will know what
> is proven, what is assumed, what is measured, and what is genuinely open.

> **Short answer.** A tokenizer has no ground truth inside itself. Its ground truth
> is the tokenizer the model was trained with, which lives outside this repository.
> So correctness is established by **agreement with an external reference**, on
> corpora that were generated by that reference. The repository does this three
> times, against two different reference implementations, and it has a separate
> script whose only job is to prove the corpora are not circular.

## The problem: a tokenizer cannot check itself

Start with why this is harder than it looks.

For most code, correctness means "the function does what its specification says."
A sort function is correct if its output is sorted. You can check that without
consulting anyone.

A tokenizer has no such internal specification. There is no property like
"sortedness" that tells you the ids are right. The ids are right if and only if
they are **the same ids the model was trained on**, and that fact lives in a file
somewhere else, produced by a different program, possibly in a different language.

This has a sharp consequence. A tokenizer can be internally consistent, pass every
round-trip test, never crash, and still be **wrong** — because it splits text
differently from the reference, and the model then receives ids it never saw in
training. The package doc says exactly this, at `internal/tokenizer/doc.go`:

> The in-kernel model remains token-id-in: no forward-pass oracle, R2/R14 gate, or
> model math test depends on this package. The tokenizer bounds kvmmu span precision
> and text-facing demos only; a wrong text/id boundary can shift a `Segment.Len` and
> evict the wrong K/V rows, but no tokenizer result certifies model numerics.

Read the last clause carefully, because it is a scope refusal and it is the honest
kind. The tokenizer package does not claim to prove anything about model numerics.
It claims to bound one thing: the text-to-id boundary. Everything on this page is
about how well that one thing is bounded.

## The answer: agree with an external reference

The strategy is to compare against a reference implementation, on inputs the
reference produced. The repository does this three times, against two different
references.

### Oracle one: HuggingFace, on SmolLM2

The first reference is the HuggingFace fast tokenizer. The test is
`TestOptionalSmolLM2EncodeMatchesHFCorpus` at
`internal/tokenizer/tokenizer_test.go:115`, and it checks this repository's `Encode`
against a corpus of text/id pairs produced by HuggingFace's own tokenizer.

The word "Optional" in the name is deliberate and worth understanding. The test
**skips** when the reference tokenizer is not cached on the machine. That keeps CI
green on a host without the model, at the cost of the gate not running there. It is
a real trade-off, and the repository takes it explicitly rather than pretending the
gate always runs.

### Oracle two: llama.cpp, on Qwen2.5

The second reference is llama.cpp, which is a completely independent implementation
in a different language. The test is `TestQwenOracleGolden` at
`internal/tokenizer/oracle_qwen_test.go:22`, and its doc comment states the design:

> `TestQwenOracleGolden` cross-validates the Qwen pre-tokenizer + BPE against the
> llama.cpp tokenizer (llama-tokenize) on the Qwen2.5 vocab — a second, independent
> oracle alongside the HF SmolLM2 corpus in tokenizer_test.go. The golden ids were
> produced by `llama-tokenize -m qwen2.5-1.5b-instruct-q8_0.gguf -p <line>` over a
> diverse corpus (ascii/code/json/cjk/contractions/whitespace), stored as
> base64(text)\tspace-separated-ids.

Two things in there matter. **"Second, independent"** — a different implementation,
so a bug shared with HuggingFace is unlikely to be shared with llama.cpp too.
**"Diverse corpus"** — ascii, code, json, CJK, contractions, whitespace. The corpus
is chosen to hit the split rules that differ between families, which is where bugs
live.

The corpus itself is `internal/tokenizer/testdata/qwen25_golden.tsv`, and its format
is exactly as described. The first three lines:

```text
SGVsbG8sIHdvcmxkISAxMjMgc3BhY2VzICBoZXJlLg==	9707 11 1879 0 220 16 17 18 12[redacted:pii:12B] 13
VGhlIHF1aWNrIGJyb3duIGZveCBqdW1wcyBvdmVyIHRoZSBsYXp5IGRvZy4=	785 3974 13876 38835 34208 916 279 15678 5562 13
ZGVmIGZpYm9uYWNjaShuKTo=	750 75698 1445 1648
```

Base64 text, a tab, then the ids. The third line decodes to `def fibonacci(n):` —
code, as promised.

### Oracle three: llama.cpp, on DeepSeek-V4.1

The third reference is the same llama.cpp family but a different model and a
different pre-tokenizer. The test is `TestDeepSeekV41JoyAIGolden` at
`internal/tokenizer/oracle_deepseek_v41_test.go:159`, and its doc comment records a
bug it was written to catch:

> `TestDeepSeekV41JoyAIGolden` pins DeepSeek-V4.1-Flash prompt ids to the reference
> llama.cpp fork token for token, without the 43 GB shard: the vocab slice carries the
> GGUF's own tokenizer.ggml.pre (joyai-llm), so this is the FromGGML path a served
> prompt takes. Before the joyai-llm hint had its own splitter it fell through to GPT-2
> ByteLevel, which splits "17" into "1","7" and diverges on the fourth probe prompt.

That is the whole failure mode of tokenization in one sentence. The splitter fell
through to a default. Nothing crashed. The ids were simply different, and the
difference showed up as `"17"` becoming two tokens instead of one. The test now pins
four probe prompts with their exact expected pieces and ids, including that fourth
one:

```go
{"What is 17 times 3?", []string{"What", " is", " ", "17", " times", " ", "3", "?"}, []int{3085, 344, 223, 1002, 2734, 223, 21, 33}},
```

Note that the expected pieces include `" "` as a standalone piece, twice. That is
the split rule from Level 2 doing something a human would not predict, and the test
pins it because the reference does it.

### Oracle four: the embedded path

There is a fourth gate, and it covers a different code path rather than a different
model. `TestGGMLEmbeddedOracle` at `internal/tokenizer/oracle_ggml_test.go:25`
checks the tokenizer that is **embedded inside a GGUF checkpoint**, rather than a
separate `tokenizer.json` file. Its doc comment explains why that path needs its own
gate:

> `TestGGMLEmbeddedOracle` proves the GGUF-embedded tokenizer path (tokenizer.FromGGML
> fed from a checkpoint's tokenizer.ggml.* arrays) is byte-exact with llama.cpp on
> the same Qwen2.5 golden corpus that gates the tokenizer.json path. This is the
> path the simpledemo relies on when no tokenizer.json is present, so a regression
> here would silently mis-tokenize the demo.

Two loaders, one corpus. That is the right shape: the same expected ids, reached by
two different loading paths, so a divergence between the loaders is caught rather
than hidden.

## The circularity trap, and the script that closes it

Now the subtle part, and the reason this repository's approach is better than it
first appears.

Suppose you write a test that asserts `Encode(text) == expected_ids`. Where did
`expected_ids` come from? If someone generated them by running *this repository's
own encoder*, the test proves nothing. It is a check that the code still does what
it did yesterday. That is a regression test, which is useful, but it is not a
correctness proof.

The repository names this trap explicitly. The script
`internal/tokenizer/testdata/verify_goldens_hf.py` exists for one purpose, and its
docstring says so:

> The Go tests assert Go.Encode == in-tree goldens against a real tokenizer.json,
> but that alone cannot tell a *true HF oracle* from a circular Go==Go check if the
> goldens were ever pasted from the Go encoder's own output. This script closes
> that gap: it re-encodes the SAME corpora with the real HuggingFace fast tokenizer
> (`tokenizers.Tokenizer`) and asserts id-for-id equality, so the goldens are
> provably HF-derived — the one corruption the issue warns must never be faked.

And it is honest about its own status:

> It is a manual reproducer, NOT wired into `go test`. Run it on a host with the
> HF model caches and `pip install tokenizers`.

So the chain of trust is: the goldens are provably external (by this script), and
the Go encoder is provably equal to the goldens (by the Go tests). Neither link
alone is enough. Together they establish that this repository's ids equal
HuggingFace's ids, without either side checking itself.

**This is the most transferable idea on the page.** Any time you have a
reimplementation of someone else's algorithm, the question to ask is not "does my
test pass" but "where did the expected values come from, and could they have come
from my own code." If the answer is yes, you have a regression test, not an oracle.

## Streaming: the decoder has a second job

Everything so far has been about `Encode`. The reverse direction has a complication
that only appears in a live system.

A model generates one token at a time. You want to show the user text as it arrives.
So you decode one token, emit the text, decode the next. The problem: a single
character in some languages is **several bytes**, and a token boundary can fall in
the middle of it. Decode half a character and you have invalid text.

The solution is `IncrementalDecoder` at `internal/tokenizer/incremental.go:23`. Its
doc comment states the contract:

> `IncrementalDecoder` turns token ids into streaming text deltas while holding
> bytes that end in a not-yet-complete UTF-8 code point.

The mechanism is `Push` at `internal/tokenizer/incremental.go:36`, which appends the
token's bytes to a pending buffer and then emits only the prefix that is complete
UTF-8, via `readyUTF8PrefixLen` at `internal/tokenizer/incremental.go:88`. The rest
waits. `Finalize` at `internal/tokenizer/incremental.go:53` flushes whatever is
left, including a deliberately incomplete final sequence, so the streaming path and
the one-shot `Decode` agree byte for byte.

That last property is tested directly. `TestIncrementalDecoderMatchesOneShotDecode`
at `internal/tokenizer/incremental_test.go:70` asserts that pushing ids one at a
time and concatenating the deltas gives exactly what `Decode` gives in one call.
That is the right invariant: streaming is an optimization, and it must not change
the answer.

## What is genuinely open

This is the part most explainers skip, and it is the part a researcher needs.

### Greedy BPE never reconsiders

The merge procedure from Level 1 is greedy. It learns `th` because `th` was the most
common pair at that moment, and it never goes back to ask whether a different early
choice would have produced a better vocabulary overall. There is no global
optimization. The result is a local optimum reached by a fixed procedure.

This is not a bug in this repository. It is a property of BPE, and every
BPE-based tokenizer shares it. Whether a non-greedy or globally-optimized
tokenization would measurably improve model quality is an open research question,
and it is not one this repository answers.

### The pre-tokenizer dispatch is a closed list

Level 2 showed the closed `preTokKind` set at
`internal/tokenizer/pretok_dispatch.go:16`. It is closed on purpose, and the reason
is the #4265 bug: two loaders with inline dispatch silently diverged, and a GLM-4
tokenizer loaded through the JSON path got the GPT-2 splitter.

The closed list fixes that class of bug. It does not fix the underlying problem,
which is that **the split rule is a per-family convention with no standard**. A new
model family means a new entry, and getting it wrong produces no error — only
quietly different ids. The dispatch is centralized so the mistake is at least
findable, not so it cannot happen.

### Some families do not use BPE at all

The `ignoreMerges` flag at `internal/tokenizer/tokenizer.go:52` exists because some
model families prefer complete vocabulary pieces over running the merge loop. And
`internal/tokenizer/spm.go` carries a separate SentencePiece path with its own
bigram queue at `internal/tokenizer/spm.go:109`. So "the tokenizer" in this
repository is not one algorithm. It is a small family of algorithms behind one
interface, and the interface is what the rest of the system sees.

### Identity is a digest, not a name

One more piece worth knowing, because it is the kind of thing that bites in
production. `Identity()` at `internal/tokenizer/tokenizer.go:277` returns a
canonical digest of every field that affects `Encode`. Its doc comment is precise
about what it is:

> `Identity` returns a canonical digest of every field that affects Encode. It
> identifies operational tokenizer behavior rather than a source path or model.

That distinction matters. Two tokenizers loaded from different files that behave
identically should have the same identity, so a cache keyed on identity does not
miss. Two tokenizers loaded from the same file that behave differently — because a
flag changed — must have different identities, so a cache does not return wrong
results. The digest is over behavior, not provenance.

## The honest summary

| Question | Answer |
|---|---|
| Is the merge loop correct? | Proven equal to a naive oracle on every fixture, under a stated monotonicity assumption. |
| Are the ids correct? | Proven equal to HuggingFace and llama.cpp on golden corpora, with a separate script proving the corpora are external. |
| Is it fast? | Measured: near-linear versus quadratic, on a fixture built to be the worst case. |
| Does it prove the model is right? | **No.** The package doc refuses this claim explicitly. |
| Is BPE the best possible tokenization? | **Unknown.** Greedy, never reconsidered, and nobody has shown a better scheme wins. |
| Can a new model family be added safely? | Only by adding a dispatch entry and a golden corpus. Getting it wrong is silent. |

The last two rows are the frontier. Everything above them is engineering that has
been done and witnessed.
