# Issue #9108 — post-drain resident GDN canary

Verdict: **REJECT**. The single authorized candidate launch occurred, so its
cardinality is consumed. The exact-owner watcher exited before its first sample
because its independent swap parser used the non-portable third argument to
`awk`'s `match()` function. The candidate never satisfied the declared
readiness predicate, no request body was sent, and no endpoint execution
identity or safety row can be accepted. There was no rerun.

This is distinct from the pre-drain #9097 result. The post-#9103 binary reached
its HTTP listener, but nine readiness probes observed `/health` HTTP 404 while
`/v1/models` returned 200. Those GETs are preserved in `candidate.log`; the log
contains no POST. Because the frozen P=32,800/T=8 body was never transmitted,
the packet does not claim a generated token, `ORCHID-7319`, the resident-GDN
forward path, Q4_K execution, or fallback status.

## Safety and isolation

The machine-wide GPU lease covered the candidate lifetime and was released with
TERM. Before launch, the named actual memorystatus source
`sysctl -n kern.memorystatus_level` read 42 percent; `memory_pressure -Q`
independently read 42 percent system-free. These are baseline observations, not
candidate minima. The watcher wrote zero sample rows, so swap growth, minimum
memorystatus, minimum system-free, targeted kernel events, and unmatched
workloads are all unbound and force REJECT. `/usr/bin/time -l` recorded
19,267,272,704 bytes maximum RSS and 35,065,373,872 bytes peak footprint before
TERM, but neither value substitutes for the missing exact-PID series.

The prior launchd-owned port-8090 service was restored under its exact command
SHA-256 `a0c13c8d7e84fa92c76db532db0a6fed13b3b42313a75e10b8f69e252f76a91d`.
Nineteen samples prove `/health` and `/v1/models` HTTP 200 continuously for 91
seconds after readiness. The GPU lease was free before this packet was written.

## Corrected scratch context

After restoration, both swap parsers were made BSD-compatible in scratch and
dry checks proved the parser, a pre-bootout cleanup no-op, and the full identity
preflight. Those checks are context only: they do not recover the consumed
launch, do not convert REJECT into KEEP, and were not used for another model
launch.

The next measured boundary is runner ownership. A new canary should not begin
until one committed runner owns a single portable metrics parser, a typed
launch/readiness/request state machine, and cleanup that can only restore a
baseline the same run actually stopped. That is tooling work, not another row
for #9108 and not a reason to reopen #9097.
